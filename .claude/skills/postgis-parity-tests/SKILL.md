# PostGIS parity tests

geodatafusion aims to behave exactly like PostGIS. The ground truth is a set of sqllogictest
(`.slt`) files whose expected results were **recorded from a real PostGIS**. Full reference:
`rust/geodatafusion/tests/sqllogictests/README.md`.

## Commands

`cargo slt` is a cargo alias for `cargo test -p geodatafusion --all-features --test sqllogictests --`.
If cargo says no toolchain is configured, prefix the command with `RUSTUP_TOOLCHAIN=<installed toolchain>` (see `rustup toolchain list`).

| Goal | Command |
|---|---|
| Test one function | `cargo slt st_area` |
| Test several | `cargo slt st_area st_perimeter` |
| One specific file | `cargo slt geodatafusion/st_area` |
| Every failure in a broad run | `cargo slt -v` |
| Which files match | `cargo slt --list st_as` |
| Full suite (what CI runs) | `cargo slt` |
| Record improved pass counts | `cargo slt --update-parity` |
| Record expected output from PostGIS | `cargo slt --complete geodatafusion/st_area` (needs PostGIS) |

A filter matches the file stem exactly (`st_area` matches `postgis_docs/st_area.slt` and
`geodatafusion/st_area.slt`). If nothing matches exactly, it falls back to a substring match.

The output looks like `FAIL postgis_docs/st_area (1/3)` plus, for each failing record, the SQL,
the error or a `[Diff] (-expected|+actual)`, and the file:line. A single-function run exits
non-zero when the numbers differ from `parity.txt`. That's expected while you work.

## Workflow: implementing or fixing a function

1. **See where it stands:** `cargo slt st_foo`. If there's no file, check
   `slt/postgis_docs/README.md`: functions without usable doc examples are listed there and need
   hand-written tests (step 4).
2. **Read the semantics** in the PostGIS docs (the URL is in the `.slt` header,
   `https://postgis.net/docs/ST_Foo.html`). Find the function's group in `plans/inventory.md`
   and implement it with that group's template (`plans/g*.md`), following `STYLE_GUIDE.md`.
3. **Iterate** on `cargo slt st_foo` until the records for your function pass.
4. **Add edge cases** in `rust/geodatafusion/tests/sqllogictests/slt/geodatafusion/st_foo.slt`.
   Write only the queries (`query T` + SQL, separated by blank lines), with no `----` results.
   Cover: EMPTY geometries, NULL input, each geometry type including collections, Z/M/ZM, SRID
   propagation, invalid geometries, and argument variants/overloads. Then record the expected
   output from PostGIS:
   ```bash
   dev/postgis.sh start            # docker or podman; idempotent
   cargo slt --complete geodatafusion/st_foo
   ```
   If PostGIS errors on a query, `--complete` records `query error`. Keep it only if
   geodatafusion should also error; otherwise fix or delete the query.
5. **Ratchet:** run `cargo slt --update-parity` (the full suite) and then `cargo slt`. It must
   print `parity.txt is up to date`. Commit `parity.txt` along with the code and tests.

## Rules

- **Never type expected output by hand, and never edit expected output to make a test pass.**
  Expected results only ever come from PostGIS via `--complete`. If you think PostGIS is
  "wrong", match it anyway or leave the test failing and say why. Don't change the expectation.
- **Never edit `slt/postgis_docs/`.** It's generated by `dev/extract_postgis_doc_examples.py`.
  Put extra tests in `slt/geodatafusion/`.
- **Never lower numbers in `parity.txt`** to get CI green. A drop is a regression to fix.
  `--update-parity` is for recording improvements, or for new files after regeneration.
- Text output is compared verbatim. That includes `ST_AsText`/`ST_AsEWKT` coordinate formatting,
  where PostGIS uses up to 15 significant digits, e.g. `2.307692307692308`. Geometry-typed and
  float results are normalised (canonical EWKT, 12 significant digits), so tiny floating-point
  differences there don't matter.
- A doc example may mention several functions (e.g. `ST_Area` with `ST_Transform`). Failures
  caused by *other* missing functions are expected. Focus on your function's behaviour.
- `'...'::geometry` literals plan through geodatafusion's `geometry` type and its `geometry()`
  cast function (`src/sql/`, `udf/native/types/`). If those are wrong, many tests fail at once,
  so check the error message before assuming your function is at fault.
- Without `--all-features`, GEOS-backed functions are missing and parity numbers won't match.
  Always use `cargo slt`.
